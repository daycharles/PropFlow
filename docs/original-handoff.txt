> **Project: PropFlow**
>
> Build the initial MVP for a modular property operations platform called **PropFlow**.
>
> PropFlow is not intended to replace Yardi, AppFolio, Buildium, Rent Manager, etc. in the first phase. The initial goal is to become the **operational layer on top of property-management systems**, focused on work orders, bulk operations, resident communication, workflow automation, asset history, and reducing repetitive property-management tasks.
>
> The long-term vision is a modular property operating system, but the MVP must remain narrow and usable.
>
> ---
>
> ## Product philosophy
>
> The application should be optimized around:
>
> * actions rather than records
> * minimal clicks
> * one workflow, one workspace
> * bulk operations
> * strong audit/history
> * configurable workflows
> * modular architecture
> * clean integration boundaries
> * excellent field/mobile usability
> * attention management rather than dashboard overload
>
> A core UX principle:
>
> **“Do the work without fighting the software.”**
>
> ---
>

> # Critical feature: bulk operations
>
> This comes directly from real property-manager pain.
>
> Users must be able to select multiple work orders and perform bulk actions.
>
> Support:
>
> * assign vendor
> * assign employee
> * change status
> * change priority
> * schedule
> * add note
> * add tag
> * send resident message
> * close
> * reopen
>
> Example:
>
> A property manager has 18 pest-control work orders.
>
> Current systems may require opening each work order individually.
>
> PropFlow should allow:
>
> Select 18
> → Assign Vendor
> → Select Pest Control Vendor
> → Schedule
> → Notify residents
> → Confirm
>
> All in one operation.
>
> ---
>
> # Work Order UI
>
> Build a work-order list optimized for action.
>
> Include:
>
> * filters
> * search

> * multi-select

> # 3. Resident Communication
>
> This is another high-priority MVP feature.
>
> Property managers should be able to send resident updates directly from the work order.
>
> Support:
>
> * SMS
> * email
> * message templates
>
> Distinguish:
>
> **Internal notes**
>
> versus
>
> **Resident-visible updates**
>
> Example internal note:
>
> “Compressor may need replacement. Check warranty.”
>
> Example resident message:
>
> “The technician completed the initial inspection. We are coordinating the next repair step.”
>
> ---
>
> # Communication automation
>
> Work-order events should be capable of triggering communication.
>
> Examples:
>
> Technician marked On The Way
> → send SMS
>
> Appointment Scheduled
> → send confirmation
>
> Appointment Changed
> → notify resident
>
> Work Completed
> → send completion message
>
> Work Cancelled
> → notify resident
>
> Build this using an event-driven architecture rather than hard-wiring every workflow into controller code.
>
> ---
>
> # 4. Timeline / Audit History
>
> Every important action should create a timeline event.
>
> Examples:
>
> * work created
> * vendor assigned
> * technician assigned
> * status changed
> * priority changed
> * appointment scheduled
> * SMS sent
> * email sent
> * resident responded
> * technician arrived
> * work completed
> * invoice added
>
> The timeline should show:
>
> * timestamp
> * actor
> * event type
> * old value
> * new value
> * related objects
>
> Never silently overwrite operational history.
>

> # Repeat repair detection
>
> Add initial logic to flag:
>
> * multiple work orders against the same asset
> * repeated similar categories within a configurable period
>
> Example:
>
> HVAC asset has 3 repairs in 120 days.
>
> Surface:
>

>
> Show:

>
> # 7. Workflow / Automation Engine
>
> Architect the product so actions are triggered from domain events.
>
> Concept:
>
> WHEN
>
> event occurs
>
> IF
>
> optional conditions are true
>
> THEN
>
> perform one or more actions
>
> Example:
>
> WHEN WorkStatusChanged
>
> IF status == “On The Way”
>
> THEN SendResidentSMS
>
> Another:
>
> WHEN WorkCreated
>
> IF category == Emergency
>
> THEN:
>
> * notify maintenance supervisor
> * set priority = Critical
> * start SLA timer
>
> Initial MVP can support a small predefined action set.
>
> Design the architecture so a visual workflow builder can be added later.
>
